# Complete iPhone Tasks with PUA

When a new chat has no valid READY proof for this chat, run the initialization flow below first, and then start the phone task; a successful earlier chat, an installed plugin, an opened widget, or a visible Runner icon does not substitute for this chat's READY. The PUA service not being started yet is a startup step that needs further handling, and you cannot end the user's task early on that basis. Existing config is reused by default, only the missing services are started, and the whole set is not reinstalled.

First determine the result the user wants delivered and the completion conditions. By default, treat an action that returned normally as having been executed as planned and keep preparing the next step; do not call an observation dedicatedly after every tap, page switch, Home, launch, or input to prove success. When the next step needs page information, read it once and judge along the way whether the previous step took effect; adjust or redo only when it clearly did not. The final key operations, the result of a send or submit, key text, and delivered files need actual result evidence.

The tool's `ok`, `verified`, `complete`, and the host's completed only describe the corresponding call, not that the whole task is complete. `action_complete` means that command has finished processing, not that the business result has been verified. A normally returned `verified=false` means there was no separate verification; it is not a failure and does not require stopping. Continue along the known path until all completion conditions are met, the key results are checked, and delivery is done; you cannot end early with "next I will read ...". For longer tasks, keep giving brief progress.

## READY and authentication

On the first use of the phone in this chat, a normal task calls `pua_ready(recover=true, screenshot=false)` by default; for text tasks keep the status / session / tree / viewport / unlock checks, and no extra screenshot is needed. If this chat already has READY and the channel has not gone stale, reuse it directly, and do not re-verify at every step. `recover=false` is only for when the user explicitly forbids restarting or explicitly asks for read-only diagnosis; do not set it proactively out of caution or let it override the user's restrictions automatically.

- `ready=true, state="ready"`: the channel is usable. Directly reuse the `observation` in READY to prepare the next step; do not immediately observe again, and do not add another round of doctor, observation, or navigation precheck.
- `ready=false, state="recovering"` or `state="recovery_required"`: with no error and MCP isError=false, it still does not mean the phone is operable. Per [startup and recovery](references/startup.md), query the same job or handle it per the user's restrictions.
- READY returns `pua_unreachable`, connection refused, `not_ready`, or an explicit service-not-started: this is the startup branch, not failure of the whole task. `recover=true` does not cold-start automatically; call `pua_setup(action="status")`, reuse an active start / recover job, or, if already configured and there is no active job, start once, and re-verify READY after the service is ready. For step-by-step instructions see [startup and recovery](references/startup.md); when config / source / build is missing, read `iphone-use-setup`.

User restrictions such as read-only and no start / restart are always kept. After recovery, reuse the new observation from READY to learn the original task's progress, and do not replay business actions that may already have taken effect.

READY is tied to the phone screen side panel, and when the host supports it, it opens or reuses this chat's existing panel by default; repeated setup / channel recovery and preview pause / resume reuse the same widget. When a panel already exists, just continue, and do not call the screen-open tool for a refresh; when you need to reopen a closed panel, call `pua_screen()` once, and do not repeat READY to open the image. When the user asks to "open the widget first so I can look", open it first and then continue initialization and the authorized task; wait only when explicitly asked to wait for their confirmation before acting. The top of the widget shows the device model and Live status, and the refresh / home screen / screenshot buttons at the bottom are only for the user to click, not tools for the model: do not call the app-only `pua_screen_frame` and `pua_screen_action`, and do not add polling, screenshots, or observe to refresh the preview. After the user clicks the home screen the page changes, so continue by the actual state seen in the next observation. A blank image, the glow effect, or a cursor does not prove READY, action success, or task completion, and is not a model observation. For preview problems troubleshoot per the [screen channel notes](references/screen.md), and do not repeatedly recover the control channel for it.

When an app actually requires a password, PIN, verification code, Face ID / Touch ID, or the phone needs the user to unlock, wait for the user to finish per [authentication takeover and recovery](references/authentication.md). For app authentication first `pua_screen(action="pause")`; `phone_locked` is already automatically paused as `device_locked`, so do not override the reason with an explicit pause. You must call the host question tool (in Default prefer `AskUserQuestion` (Claude Code) / `functions.request_user_input_async` (Codex)), with the first option fixed as "Done, continue" and the second possibly "Cannot complete right now". An asynchronous return / preselection is not a user reply; during the takeover pause phone actions, reads, and screenshots, and do not ask for credentials. After the actual completion notice, for app authentication or a legacy unknown pause first `pua_screen(action="resume")` and then get a fresh observation; for a device unlock, re-verify READY, which on success only lifts that same lock-screen pause automatically. READY's `preview.paused` / `pause_reason` describes the preview state; a successful READY cannot be taken as app authentication being done. Continue the remaining work by the new state.

In Claude Code there is no side panel. If the user wants to watch the phone, tell them to run `python3 <PLUGIN_ROOT>/scripts/mirror.py` in a terminal (live browser mirror at http://127.0.0.1:8765); do not call `pua_screen_frame` or `pua_screen_action` yourself.

## Choose observation by what the next step needs

For a known unique semantic target and a known navigation path, use the default `observe="none"`, and you can execute in succession or merge into a batch. When the next step needs to recognize an unknown page, pick an area, or read content, set `observe="tree" / "screenshot" / "both"` directly on this action, and use the returned nested `observation` to both plan the next step and judge the previous action along the way. Do not first use none and then dedicatedly observe as verification, adding a model turn. For a standalone read use `pua_observe(mode=...)`, and do not mix mode with observe.

Each node of the tree keeps just one copy of each fact: `type` has no `XCUIElementType` prefix, and `rect` is `[x, y, width, height]` (iPhone points); no `name` means it equals `label`, no `value` means it equals the text, and no `enabled` / `visible` / `in_viewport` means true. Keep `include_invisible=false`, `max_nodes=100`, `expensive_visibility=false`; to look up a single target use `pua_find` / `pua_wait`, and do not fetch the whole tree repeatedly. A truncated tree or a node in the viewport does not prove the content is complete or the target is unobstructed, since fixed headers and overlays may cover it.

Take a screenshot only when custom-drawn content, occlusion, or missing labels need visual judgment. The screenshot comes back as an image in the same result, already scaled to a readable size: multiply image pixels by `[x, y]` of `image.pixel_to_point` to get iPhone points, and do not convert from the raw resolution or the Mac screen. screenshot skips XML; both provides the tree and the image. If the app shows a share sheet, handle the current state, and do not loop screenshots repeating the same path.

## When the UI is abnormal, look at the screenshot first, then decide the action

The screenshot is the general fallback for UI anomalies. For selector / focus failure, no tappable target found after scrolling, scrolling with no progress, a blocked region or changed context, an input read-back mismatch, or the expected page not appearing, first look at the current screenshot in the result and then decide the next action; when no usable screenshot exists, take one `pua_observe(mode="screenshot")`. Do not first re-read the whole tree, change label spelling, increase the number of scrolls, or retry unchanged. A truncated tree, a coordinate tap that clearly did not take effect, or a page that differs from expectations are also handled by this flow. A plain `verified=false` is still not an anomaly and does not require a screenshot at every step.

From the screenshot, first judge the current page, whether the first and last rows moved, end-of-list controls / blank space, pop-ups / fixed headers, and the actually scrollable region. Stop looking once the target or the task-scope boundary has been seen; if the image no longer moves, first handle the boundary or occlusion, then decide whether another region or direction is needed. `direction` is always the finger's movement direction, and up usually views the content below. The user's side-panel live preview does not replace the model actually looking at the tool image.

- Tapping: `tap_point` and the candidates' `tap` are the element position (iPhone points) and do not prove it is tappable. Coupons, ads, menus, or login overlays may cover background controls; from the screenshot first find the close / cancel button that is actually visible, deal with the cover, and then tap the target.
- Typing: first tap the input field that is actually visible in the screenshot, then call `pua_type_text(text=...)` without a selector. `no_focused_field` means nothing was typed; the previous tap may have been intercepted by an overlay or landed at the wrong position, so do not repeat that same set of coordinates and input unchanged. Reselect the point from the current screenshot, and when the next step needs information, have the action return a screenshot so you can judge the page and focus.
- Target off screen: first swipe toward the target, then tap by the screenshot that follows. When waiting on a label or a scroll-find fails, also continue by the real image, and do not loop on the same label.

Convert a screenshot pixel point `(px, py)` to `x=px*image.pixel_to_point[0]`, `y=py*image.pixel_to_point[1]` before passing it to `pua_tap`. x/y accept iPhone points, and you cannot pass screenshot pixels or Mac widget coordinates directly.

When calling tools through `functions.exec`, you must actually forward the image to the model, and cannot `text(result)` the whole result containing base64:

```javascript
const result = await tools.mcp__iphone_use__pua_observe({mode: "screenshot"});
for (const block of result.content ?? []) {
  if (block.type === "text") text(block.text);
  else if (block.type === "image") image(block);
}
```

Forward the image blocks of failed results from taps, input, and so on in the same way. If the image was not forwarded successfully, open the returned `image.path` / `error.observation.image.path` with `view_image`; image metadata or base64 cannot count as having seen the screenshot.

The above is for recoverable UI-targeting problems. Fix argument errors per the schema, recover READY for channel faults, and let the user complete lock screen / authentication and the like. When it is uncertain whether an action took effect, read the real state first, and do not replay input, send, order placement, or the whole batch; an ordinary occlusion that a screenshot is enough to handle should keep being tried, and do not hand the task back to the user early.

## Apps and routine actions

A bundle ID that is already known and verified can be launched directly; to look up common apps offline use `pua_apps(source="catalog", query=...)` or the [common app catalog](references/apps.md). For an unknown or same-name app use `source="auto"` to look up local candidates, and only query Apple if there are still no results. Do not guess IDs in a row; the China Merchants Bank main app is `com.cmbchina.MPBBank`. A store or catalog record does not prove local installation, and `installed_verified=true` is the evidence of installation. The observation that prepares the next step after launch also shows the actual foreground, and no extra default foreground verification is added.

- `pua_launch_app`: activate once and continue; default `verify=false, observe="none"`. When the next step needs new page information, set observe; only when a key entry truly needs to prove the target app / page, explicitly use `verify=true` or pass `expect`.
- `pua_tap`: prefer `selector`, copying label / name / value / type from the current node, and optionally adding enabled; for labels that are long or contain changing times or numbers use `label_contains`. Use the predicate on its own, and keep the line breaks, quotes, and backslashes in the actual label; rect, visible, and in_viewport are not selector fields. When same-name matches are stacked at the same position (such as a Cell and the text inside it), or only one is on screen, the tool itself picks that target and explains it in the result's `target`; multiple separate matches return `ambiguous_target` with candidates carrying `index`, type, position, `tap` coordinates, and `hittable`, and you tap by the `tap` coordinates of the target among them (or use the same selector plus `index`), do not casually pick the first, and no further observation is needed for this. When the selector fails or is semantically insufficient, use iPhone point coordinates x/y; observation_id is optional, and when provided must come from the same Runtime and only checks the app / viewport context. When the existing page information is enough to locate, do not additionally read the tree or screenshot; after a page switch, user takeover, or rotation, relocate by the current information.
- `pua_press_button`: use only buttons supported in the schema. Home uses the dedicated homescreen path with default `verify=false`, and a normal return is enough to prepare the next step; when the home screen state is explicitly needed, set `verify=true`. When the MCP binding is unavailable, continue the same authorized action per [tool failures and code calls](references/tool-fallback.md).
- `pua_swipe`: the direction is the finger's movement direction, and up usually browses the content that follows. Default `verify=false, observe="none"`; it performs the gesture only once and does not read XML to verify progress. You can pass region per the known list, and observation_id or tree is not mandatory. When the next step reads list content, judge along the way whether it moved; if it clearly did not move, first look at the entry point, boundary, overlay, or region in the screenshot. An explicit `verify=true` only checks the geometric change of one gesture; no progress or a context change hands back to the model with a screenshot attached, and even with the legacy `max_attempts=2` passed it does not automatically retry with a different gesture.
- `pua_wait`: use a bounded timeout when you truly depend on a control appearing; no fixed long sleep is needed, and do not add a wait for all navigation. `pua_scroll_find`: if the target is already tappable, return directly; on occlusion or ambiguity, stop immediately with a screenshot. One call swipes at most once; if there is still no tappable target after scrolling, first look at the returned screenshot and then judge whether to keep swiping; `max_swipes=0` only looks up, and a positive value, even above 1, does not swipe blindly in succession. After finding it, continue with the next step, and do not look up the same result again.

`expect` and `verify=true` are explicit verification options, used for the final key state or an actual dependency, not required at every step. HTTP accepted and business success are different facts; run routine tasks optimistically, and base the final conclusion only on key results. On an explicit error, uncertain input / submit, or a partially completed action, look at the actual state first and then decide the remaining steps.

## Input and sending

Directly use `pua_type_text(selector, text)` to give the full content the user needs in one go; do not first write short test text or ASCII, and do not split it into segments yourself. When the selector cannot find the input field, do not retry with different spellings: tap the input field by coordinates and then call `pua_type_text(text=...)` without a selector to type into the current focus. Defaults are `replace=true, allow_newlines=false, submit=false, verify=false, observe="none"`; after ordinary search, filter, and similar input you can go straight to the next step, and for an unknown next page return an observation on this action and judge along the way. When existing drafts need to be kept, decide to replace or append by the current content; for key final text you can explicitly `verify=true` to check the full field. Passwords, phone unlock codes, and verification codes are entered by the user.

Long text is typed in segments by the tool. When the result is `input_complete=false`, the text is not fully typed yet: call `pua_type_text` once more with only the returned `continue_token`, without resending the text or attaching other parameters, and do not tap, swipe, or switch pages in between; once everything is typed, the verify / submit / expect / observe of the original call then run. When the continuation expires (`input_continuation_expired`), nothing is typed; first read the actual text of the field, then use `replace=false` to add only the missing part. An error mid-input carries `characters_confirmed`; likewise read back first, and do not retype the whole piece.

Multi-line content may trigger Return as send in a chat control. Set `allow_newlines=true` only when you know for certain that the current TextView is a suitable multi-line editor; you cannot quietly change the format the user asked for into a single line. Allowing newlines does not equal authorizing send. When the user has authorized sending, check the target conversation and full draft in one observation or an explicit input verification before sending, then send once; after sending, check the final content and the send count. `submit=true` does not prove the submission result, and after submitting, verify by the real result page / record. Only when it is clearly unsent should you do it again; do not auto-resend based on a timeout, a missing separate verification, or a plain `verified=false`.

For WeChat chat messages, organize them into a single text without line breaks where possible, then type and send it in one go, to avoid the chat box interpreting Return as send. When multi-line layout is truly needed, do not hand a whole block containing `\n` directly to `pua_type_text`: first type the content as a draft and confirm focus is in the WeChat input box, tap once on a blank spot inside the input box to bring up the text-editing toolbar, then tap "Line Break" in the toolbar to insert a line break; repeat as needed, and after finishing check the full draft, then tap "Send" separately once. If the toolbar does not appear or has no "Line Break" option, stop and relocate by the current UI, and do not substitute the keyboard Return. This depends on the current WeChat version and the toolbar actually shown in the input box (the labels follow the app's UI language); you cannot infer that a line break was inserted safely from `allow_newlines=true` alone.

## Continuous execution and list collection

Use `pua_batch` to merge known short paths, at most 20 steps; routine tap, launch, Home, input, and scroll need no expect, and a plain `verified=false` does not block later steps. You can put one observe at the end of the plan, or observe only at the position where the next step needs information. An explicit error, an uncertain action, or an unverified submit will stop it; long text that is not fully typed (`stop_reason="input_continues"`) or reaching the single-call time budget (`"time_budget"`) also stops it. Continue the remaining steps by completed_steps / stopped_at and each step's result, and do not replay the whole batch. Split into segments when an unknown page, authentication, or a dynamic pop-up needs new information, and do not mix unauthorized sending into navigation.

When looking for a record at an unknown position, do not pre-pack multiple same-direction swipes into a batch. Swipe one step first and read the page the next step needs; when the tree is truncated and the end cannot be seen or the page makes no progress, take a screenshot and then judge whether to continue. Known short paths can still be merged, and stop scrolling once the task scope or the end of the list has appeared.

`pua_collect_list(row_type="Cell", max_pages=6)` collects within bounds up to 10 pages, swiping only once each time and directly collecting the new page, reusing the full tree and viewport; it judges duplicate pages by the target rows, does not discard a new page just because all labels of a virtualized list changed, and does not try a backup gesture. It returns rows, pages, and stop_reason, and complete is always false; identical type/name/label/value are deduplicated, and records that actually display the same may be collapsed. You can pass end_selector as coverage evidence, and in the end check the scope, count, total amount, dates, and missing fields as the user requires; hitting the limit or making no progress cannot be taken as complete. When detail fields are insufficient, go into detail reads, and entering each detail does not require a separate verification. For the specific key verification see [collection and input verification](references/verification.md).

## Adjust on explicit anomalies

`occluded_target` fails before the click, no click was sent, and you also cannot infer that a failed click opened an overlay. Look at the screenshot attached to the error: if the target is visible, tap by coordinates at `tap_point` directly; if an overlay, picker, or fixed header truly covers it, first deal with it (a real close entry or a safely dismissible spot outside the panel) and then continue. For `offscreen_target`, first swipe the target onto the screen. A custom half-screen panel may have no native Alert / Sheet node; go by the screenshot, and do not conclude there is no occlusion just because the background tree still has buttons.

An explicit scroll verification returning `no_scroll_progress` only means the gesture was executed but list movement was not proven, and does not prove an empty list or the end. That anomaly, `scroll_context_changed`, and a region blocked by an overlay all attach a screenshot, even if `observe="none" / "tree"` was requested; reuse a screenshot already in the result. A list collection stopped by a duplicate page also attaches a screenshot, keeping the rows already collected and the coverage limits. Look at the image first and then handle the boundary, overlay, or region, and do not blindly add attempts; ordinary gestures still do not read the tree additionally for verification.

`action_executed=true, action_complete=false` or `uncertain=true` means the action or some steps may have taken effect; for input, send, payment, order placement, and the like, read the actual content / records first, and do not replay the whole operation. A brief failure of a pure query can be re-read by the tool within bounds, which is not the same as having executed a phone action. `local.pid.0`, `pua_foreground_unavailable`, or XCTest Code 41 is a channel fault; recover per the READY guidance, reuse the new observation to continue the remaining task, and service recovery does not replay business actions.

When the tool binding fails you can use the plugin's code entry, reusing the same config, session, and operation lock; do not give up just because MCP is unavailable, and do not create a parallel control session. `pua_metrics` provides HTTP and tool latency, the bytes returned by each tool, and the wait between two tool calls (the sum of host, model, and user time); measure optimization results by actual task time and delivery completeness, and do not describe omitting per-step verification as the business having been proven.
