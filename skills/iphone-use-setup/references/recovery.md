# Channel Recovery

This applies when the PUA service is running but the XCTest channel has failed. If the service was never started, handle it per "Continue initialization when the service is not started" in SKILL; for signing, trust, and connection problems see [troubleshooting](troubleshooting.md).

If navigation reports `XCTDaemonErrorDomain Code=41` / `Not authorized for performing UI testing actions`, or the current app becomes `local.pid.0` / `pua_foreground_unavailable` and cannot be observed, do not treat `status.ready=true` as proof that it is operable. This is a PUA / XCTest channel fault and cannot be solved by changing selectors. `pua_observe` stays read-only and gives READY guidance; call `pua_ready(screenshot=false)` first. A stale foreground clears the old session and observations and reads once more; on success it returns `recovery.state="read_recovered"`. Only a persistently stale foreground or an XCTest authorization error enters service recovery, and it does not replay failed navigation, input, or submission.

Automatic recovery only restarts a service of this plugin whose config, endpoint, worker identity, and actual port listener ownership have all been verified, reusing the matching valid build. When `ready=false, state="recovering"`, record recovery.job_id, query the existing job with the given status parameters, find the matching id in the `jobs` array, and check recovery_phase: stopping, then starting, then serving. Once serving is reached, re-verify READY and reuse the new observation in it directly to learn the task progress, without starting again; the long-running Runner may stay running, so do not wait for succeeded. Query by job phase and logs, not with a fixed 15 seconds x 20 loop, and do not swallow response parsing errors. recover=false does not initiate an automatic restart, but can report an existing recovery job. This state has no error and MCP isError=false, and still does not mean READY or that the whole task is complete.

`ready=false, state="recovery_required", reason="recovery_disabled"` means automatic recovery was turned off for this call. When the current user instructions allow recovery, call once more per the recovery's next_tool / next_arguments; when the user explicitly forbids restarting or asks for read-only diagnosis, report the channel blocker and keep the restriction, and do not change it to true automatically. This state is also a normal diagnostic result; actual recovery refusal, cooldown, lock screen, and unclassified faults still return errors.

When `pua_recovery_required` is returned, handle it according to the reason in recovery: the cooldown is 120 seconds, so respect the returned retry_after_seconds and check the most recent recovery log; for an external PUA, unknown ownership, a port already taken by another service, or a missing build, keep the existing service and perform the exact manual steps. When a manual restart is truly needed, use status to find this plugin's job whose ownership has been verified, stop it and confirm it has stopped, then start; leave an external service to its owner to restart, and do not kill by port or change the run directory to bypass the checks. If an authorization error still appears after restart, check Developer Mode and "Developer > Enable UI Automation" on the unlocked iPhone per the current prompts; trust or authentication confirmation is done by the user.
