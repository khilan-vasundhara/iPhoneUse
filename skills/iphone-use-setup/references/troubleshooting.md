# Recovering by Blocking Layer

| Symptom / log | Check first | Next step and verification |
| --- | --- | --- |
| No real device found, device unavailable | Whether the cable supports data, whether the phone is unlocked and trusted, whether Xcode has finished pairing | Reconnect and discover; confirm the result is the target real device, avoiding a simulator or another device by mistake. |
| Xcode has not finished first launch, license, or components are missing | The developer directory, Xcode version, and first-launch state returned by doctor | The user installs full Xcode and completes the system prompts, then run doctor again; installing Command Line Tools alone is not enough to build PUA. |
| iOS version / developer disk image incompatible | Current iOS, the selected Xcode, and the device preparation error | Update or choose a suitable Xcode per the compatibility info, then finish device preparation; do not retry the same binary endlessly. |
| Developer Mode disabled | The Developer Mode switch on the phone and the confirmation after reboot | The user enables it and reboots, discover recognizes the device again, then start; a device visible before the reboot does not mean the new state is prepared. |
| signing requires development team / no signing identity | Apple Account, Team, and development certificate in Xcode | The user signs in to Xcode and picks their own Team, then configure/build; do not put account passwords in config files. |
| bundle identifier cannot be registered / no profiles | The Runner target's bundle ID and team provisioning | Reconfigure with a bundle ID the user's team can sign; consider the `.xctrunner` suffix of the XCTest Runner; build again to verify. |
| maximum number of apps for free development profiles | Whether the Personal Team already has 3 development apps | State the limit the system points out; the user decides whether to uninstall development apps they do not need, or use another valid team they already have; do not delete apps automatically, and do not push them to buy a developer program. |
| profile / certificate expired, old Runner no longer launches | Signing validity and profile expiry in the build log | Rebuild/start with the original local config and re-verify READY; free profiles often need re-signing after 7 days, check the current profile for specifics. Do not just reopen the port. |
| developer not trusted / unable to verify | The developer entry on the phone, network, and Xcode prompts | The user completes trust or verification in the current developer entry and checks the network per the system error; do not revoke shared certificates of other projects. |
| build succeeded, but HTTP unreachable | Whether the Runner test is still running, the USB forwarding process, and the local port | Use status to separately confirm running and forwarding, then start to recover; do not treat BUILD SUCCEEDED as READY. |
| Port conflict | Whether there is already a forward for the right device or an unrelated program | A correct forward can be reused; otherwise configure a free local port. Do not kill processes of unknown ownership. |
| HTTP status reachable, session or source fails | The device, PUA session, device lock screen / test process the service corresponds to | Read the error and status first; if necessary rebuild the session / restart the Runner; re-verify a valid viewport and the current observation. |
| stale element reference with local.pid.0 / pua_foreground_unavailable | Whether PUA / XCTest can resolve the current real foreground; do not look only at status.ready | Call pua_ready; re-read the session / UI only once, and for persistent faults follow the recovery to track the background service recovery with verified ownership. Old observations and element IDs are void. |
| XCTDaemonErrorDomain Code=41 / Not authorized for performing UI testing actions | The test process authorization state and the phone's developer settings | Call pua_ready to track recovery; if it still fails, the user checks unlock, Developer Mode / Enable UI Automation, and trust prompts; do not retry key presses repeatedly. |
| ready=false, state=recovering | The setup status and logs for recovery.job_id | A normal not-ready state; do not treat isError=false as READY. Poll the same job until recovery_phase=serving, then re-verify READY. The Runner is a long-running service and may stay running; do not start again or wait for succeeded. |
| ready=false, state=recovery_required, reason=recovery_disabled | Whether this call set recover=false, and whether the user explicitly forbade restarting / asked for read-only diagnosis | When instructions allow recovery, call recover=true per recovery.next_tool / next_arguments; with an explicit restriction, keep it and report the channel blocker. The first READY of a normal task uses the default true, and recovery is not turned off proactively for precheck or caution. |
| pua_recovery_required, recovery.state=cooldown / manual | Remaining cooldown, config, worker and listener port ownership, a valid build | During the 120-second cooldown diagnose per retry_after_seconds; for unknown ownership or an external service, do not kill by port, and recover with the manual steps returned. |
| HTTP timeout after a tap, input, or submission | The actual page / field / message in the observation needed next | Input / submission and the like may have taken effect; look at the actual result first and then continue the remaining steps, and do not replay automatically. A pure query can be re-read within bounds and is not treated as a mutation. |
| action_executed=true, action_complete=false | The real state after at least one accepted action | Read back first even if uncertain=false; do not replay the full input, submission, or batch; channel recovery only restores read / control capability and does not replace business verification. |
| App asks for login, password, or biometrics | The target app's current authentication prompt and normal entry | Per [authentication takeover and recovery](../../iphone-use/references/authentication.md) prompt the user to finish personally; pause phone calls during the takeover, and after the completion notice re-observe to check the app / target page and continue the original task. READY cannot mean the app is logged in, and app authentication itself does not require restarting PUA. |
| PUA works, but the control tree lacks content, or label targeting fails | Whether the page is custom-drawn, protected, or the tree is truncated | Do not retry with other labels: switch to a coordinate tap using the screenshot attached to the failure result; for input, first tap the input field, then call `pua_type_text` without a selector. If it still cannot be observed, report the specific limitation. |

status returns a `jobs` array; match the requested job_id by id, and do not read a nonexistent single job or swallow parsing errors. For fetch / build, look at the completed or failed terminal state; an ordinary start is a long-running service, so call READY once `service.ready=true`, and do not wait for the Runner to become succeeded. For recovery jobs, re-verify READY after recovery_phase=serving. Query based on the current phase, logs, and retry_after_seconds, not with a fixed long interval, and do not start repeatedly.

READY comes with the current observation; reuse it directly to prepare the next step. Routine tap, Home, launch, input, and scroll run optimistically by default; a plain verified=false does not require stopping or a separate observation. When the next step needs an unknown page, return the needed observation on that action and judge progress along the way; only the final key result gets an explicit expect / verify or a final read-back. Known coordinates / regions do not need a separate image or tree read for an observation ID; if an ID is used, it must come from the same Runtime and match the app / viewport.

The PUA path does not depend on the Mac's iPhone mirroring window, the display origin, or the mirroring lock-screen mutual exclusion, but device lock, user actions, USB disconnection, and the app's authentication policy still change the real-device test state. Recover only from the current channel evidence, and do not apply the "mirroring requires locking the phone" steps.

Signing references: [Apple Personal Team](https://developer.apple.com/help/account/basics/about-your-developer-account), [Appium provisioning](https://appium.github.io/appium-xcuitest-driver/latest/getting-started/provisioning-profile/), [Appium automatic signing](https://appium.github.io/appium-xcuitest-driver/latest/getting-started/provisioning-profile/auto-config/). Verified on: 2026-10-06.

## Mirroring and PUA occupation conflict

`mirroring_conflict`, an empty tree on the Settings page, or a lock-screen screenshot saying "This iPhone is being used from a Mac": exit the Mac's iPhone mirroring, have the user unlock the phone if necessary, and call pua_ready again. Do not continue the task in the empty-tree state by repeating launch, tap, or forced input. The mere existence of the mirroring process does not prove occupation; the tool refuses READY when the tree is empty and mirroring is running.
